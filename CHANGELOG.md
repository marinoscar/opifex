# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

**Convention, enforced by CI:** every pull request that ships a `feat` or
`fix` (per this repository's commit-type vocabulary) adds its own bullet under
`[Unreleased]`, grouped by the `VISION.MD` §12 phase it belongs to, as part of
that PR — not retroactively. `chore`, `docs`, `refactor`, and `test`-only
changes are exempt.

`scripts/check-changelog.mjs` fails a pull request whose commits include a
`feat` or a `fix` and whose diff does not touch this file; it runs as a step in
CI's `Lint` job (#312). There is no opt-out, because the commit type is the
opt-out — a change that genuinely warrants no changelog line is a `chore`, a
`refactor`, a `test` or a `docs` change, and the vocabulary already says so.

What the gate checks is that this file appears in the diff, and nothing more.
Whether the bullet says anything useful is not mechanisable and is left to
review: **the check enforces the habit, review enforces the content.**

## [Unreleased]

> **Before deploying this: several things changed what it takes to start or operate the API.**
>
> - **Opifex no longer ships inert.** `runners.claudeCodeLocal.enabled`, `dispatch.enabled`, `dispatch.allowPreviewRunner`, `github.writesEnabled` and `reconciler.enabled` now all default to **true**, and `dispatch.hardSpendCeilingUsd` still defaults to unset — so a fresh install is _ready_ rather than _running_: the runner registers, the queue drains, GitHub writes are permitted, and **no work order dispatches until an operator names a spend ceiling**, because an unset ceiling refuses every dispatch before anything else is considered. Two things follow for an existing deployment. First, if your `.env` sets any of these four to `false` explicitly, nothing changes for you — the environment is still the layer under the Control Center row. Second, if it does not, upgrading turns them on: writes become permitted (though still only to repositories whose own `mirrorLabelsEnabled` / `specFeedbackEnabled` flags are on, which still default off per repository), and dispatch begins the moment a ceiling exists. An operator who wants VISION §12's read-only observation week now turns `github.writesEnabled` **off** deliberately, rather than getting one by never turning it on. `reconciler.enabled` is the fifth flag and #439 did not name it: it gates the entire loop — observation, projection, liveness, the watchdog, escalations, notification delivery, spec feedback and the dispatch drain — so flipping the other four without it would have left a fresh install doing nothing, with the reason moved rather than removed. (#439, ADR-0019, partially supersedes ADR-0007)
> - **Every boolean operator setting now accepts `true`/`false`, `1`/`0`, `yes`/`no` and `on`/`off`, in any case.** It used to accept the exact strings `'true'` and `'false'` only, and fall back to the declared default for anything else. That was fail-safe while the switches that spend money or act outwardly defaulted off, and the defaults above reverse it: `GITHUB_WRITES_ENABLED=no` was discarded and writes came up **on**, while the operator read their own `.env` and believed otherwise. A value that is still unreadable (`enabled`, `2`, an empty string) continues to fall back to the default, and is now logged at **ERROR** rather than warn, naming the variable, the value it could not read and the value actually in force. (#439)
> - `JWT_SECRET` is now required and validated at boot: unset, or under 32 characters, and the API refuses to start — the startup failure names every invalid variable at once. Generate one with `openssl rand -base64 32` (44 characters, comfortably over the floor). (#278, #295, #309)
> - `POSTGRES_PASSWORD` is now required when `NODE_ENV=production`: an unset value, an empty value, and the literal `postgres` default — the value `infra/compose/.env.example` ships, so copying that file is not choosing a password — are all rejected at boot. Outside production the default still applies with no enforcement, so a local `docker compose up` stays frictionless. (#299, #306)
> - `GET /api/health` (the comprehensive check — not the liveness or readiness probes) now fails when no runner is registered and routable, the way it already failed on seed drift. `GET /api/health/ready` deliberately does **not** fail on either condition: it reports the finding and stays up, because the container that would go down under `restart: unless-stopped` is the same one running the fix (registration convergence, or `prisma:seed`). (#277, #294)
> - `OPIFEX_HARD_SPEND_CEILING_USD`, `SUPERVISOR_HARD_SPEND_CEILING_USD` and their two window variables are no longer the last word: a row written from the Control Center wins over them, and both ceilings now change at runtime without a restart. A deployment that sets them in `.env` and never opens the Control Center behaves exactly as it did before — the environment is still the layer under the row. This reverses a guarantee stated in prose in several places, deliberately and only because both containment barriers are in force; see ADR-0018 §6. (#345, #334, #346)
> - The GitHub, runner, dispatch, reconciler, supervisor, promotion and notification-delivery variables are now read through the operator settings registry rather than manufactured in `configuration.ts`, and the registry validates them. Values it rejects — a non-integer where a number is expected, or a number outside the declared range, such as a `GITHUB_REQUEST_TIMEOUT_MS` below 1000 — no longer take effect: the declared default is used instead and the reason is logged once — the first time that setting is read — naming the variable and what was wrong with it. Nothing refuses to boot over one, deliberately, since a mistyped reconcile interval is not a reason to take an API down. Every value that was already valid resolves exactly as it did. (#340, epic #332, ADR-0018)

### Added

#### Phase 0 — Conventions

- **CI**: GitHub Actions pipeline (`.github/workflows/ci.yml`) with `lint`, `typecheck`, `test-api`, `test-web`, and `build` jobs, running on pull requests and pushes to `main`. The provenance check lives in its own workflow (`.github/workflows/provenance.yml`, #179) so that editing a pull request body re-runs it without re-running the whole pipeline; it is pull-request-only, since a push to `main` has no PR body to carry a closing keyword.
- **Provenance enforcement**: `scripts/check-provenance.mjs` fails a pull request whose body carries no closing keyword, whose commits are missing a required trailer, or that names a decision resolving to no file under `docs/adr/`. Its patterns are read out of `docs/PROVENANCE.md` at run time so the check and the specification cannot drift.
- **Changelog enforcement**: `scripts/check-changelog.mjs` fails a pull request whose commits include a `feat` or a `fix` and whose diff does not touch `CHANGELOG.md`, wired as a step in CI's `Lint` job. It walks the branch's own first-parent line, so a merge of `main` carrying somebody else's `feat` does not fire it. The check verifies only that the file is in the diff — the content is review's job (#312).
- **Architecture decision records**: `docs/adr/` with a template, an index, and the numbering, lifecycle and supersession conventions (`docs/adr/README.md`); recorded as ADR-0009. Every ADR names its discussion issue, and CI enforces it.
- **Linting and formatting**: ESLint (flat config) and Prettier across both workspaces, replacing the `echo 'No linter configured'` stubs. `npm run lint` and `npm run format:check` are real and CI blocks on both.
- **Dependency updates**: Dependabot configuration (`.github/dependabot.yml`) for weekly npm updates across the root, `apps/api`, and `apps/web` workspaces, plus weekly GitHub Actions updates.
- **Governance**: GitHub issue templates (Epic, Feature request, Bug report, Decision proposal), a pull request template with required provenance trailers, a machine-readable label taxonomy (`.github/labels.yml`), and `.github/CODEOWNERS`.

#### Phase 1 — Contracts

- **Contracts**: `schemas/work-order.schema.json`, `schemas/runner-capability.schema.json` and `schemas/run-event.schema.json`, with worked examples, invalid fixtures and a conformance suite that asserts each fixture is rejected for the reason it was written for.
- **Contract types**: TypeScript generated from the three schemas by `npm run contracts:generate` into both `apps/api` and `apps/web`, so the cockpit and the API cannot disagree about a shape. `npm run contracts:check` fails the build when a schema changes and the generated output does not.
- **Boundary validation**: work orders are validated before they become an authorization record and an execution record, capability manifests before a runner enters the fleet, and run events at ingestion. Failures name the offending field.
- **Schema versioning**: `schemaVersion` accepts the whole `1.x` range with `default` naming the version a producer should write; one schema file per major, and the old file stays so a persisted work order remains re-runnable. Policy recorded as ADR-0010.
- **OpenAPI**: `npm run openapi:dump` and `npm run openapi:lint` are wired and enforced in CI against a Spectral ruleset; the document is generated rather than committed.

#### Phase 2 — Reconciler, read-only

The control loop that everything else now runs on top of exists, and for this phase it can only look. Each tick it observes GitHub and the run state in Postgres, computes what should be true, and records the diff — it holds no GitHub write client, so it cannot act on what it observes (epics #15, #16; #131, #133). An eligible issue projects into a work order and that projection is persisted on the tick, ahead of anything that could execute one (#155–#158). `retryCeiling` and `rateLimitReserve` are now read once at the top of each tick instead of frozen at process construction — the coherence unit is one tick, not the process lifetime — and that snapshot, plus `writesEnabled`, is now persisted on `reconcile_ticks.settings` and returned from `GET /reconciler/ticks` and `GET /reconciler/ticks/:id`, so a reviewer can tell which ceiling or which GitHub write mode a given tick ran under from the row alone. `NULL` on this column means the tick predates the snapshot, never that it ran with defaults (#342, epic #332).

#### Phase 3 — Liveness and escalation

The failure the project exists to fix — a stalled session going unnoticed for hours — now has a watcher. The watchdog computes a verdict on a run and escalates to a human; it does not kill or re-dispatch anything itself, since that is Phase 4 machinery by design (epic #17; #135). A failed escalation delivery now retries instead of being dropped (#137), and a parked approval whose escalation never raised is completed later by a backfill (#237, #280).

#### Phase 4 — Execution

Work orders now actually run. `claude-code-local` is the first runner: it streams a Claude Code session, maps its output to run events, and enforces its own concurrency limits, reaping and shutdown (#139, #144–#146, #148). The reconciler's dispatch queue routes a work order to a capable runner, enforces concurrency, and drains on every tick (#142, #152, #160). A hard spend ceiling and a wall-clock deadline are enforced from the control plane, and can act once passed (#176, #181, #188). A work order that has used all its retry attempts is quarantined rather than retried forever, and a pull request is held back from review until CI is green (#200, #201). Runs conclude correctly on their terminal event — including a stalled run that would otherwise hold its dispatch slot forever — and survive a runner child process that never reads its prompt (#203, #258, #255). A work order can declare a required model tier and dispatch routes on it, with a distinct refusal reason when the tier can't be met (#206, #293, #311). Runner registration now converges instead of only running once at boot, so a runner that starts late is still picked up (#276). The API image now ships `git` and the Claude Code CLI, without which `claude-code-local` could execute nothing at all in the containerized deployment: ADR-0008 makes the runner a child process of the API process, `claude --version` could not be probed, and the fleet correctly reported itself unavailable. `git` was the blocker that fired first and the less obvious of the two, since the workspace service shells out to it for clone, checkout and commit before the CLI is ever invoked (#325). Enabling the runner in a container now has a documented credential path, and neither option is defaulted: `CLAUDE_CODE_OAUTH_TOKEN` draws on the same subscription quota as your own interactive use, while `ANTHROPIC_API_KEY` bills per token against the spend ceiling. The choice is deliberate rather than inherited because `claude --version` succeeds without credentials, so an unauthenticated CLI would otherwise register as an available runner and fail every run at auth — the deceptive failure, where a missing binary is the honest one. Runner workspaces and CLI state now survive an image rebuild, which is what keeps a re-submitted work order a reuse rather than a fresh clone (#326, #327). The agent subprocess now inherits an explicit allowlist of environment variables rather than the whole of the API's own, so `JWT_SECRET`, `POSTGRES_PASSWORD`, `GITHUB_TOKEN` and `SUPERVISOR_MODEL_API_KEY` are simply absent from it — with the first an agent could mint an admin token against the control plane supervising it, and with the second reach the database behind it. An allowlist rather than a denylist because a denylist has to predict every future secret name, and the settings work ahead will introduce dotted-path keys that no denylist written today would contain; the CLI's own credential and the git token the workspace's credential helper reads are carried through deliberately (#334).

#### Phase 5 — Cockpit

The web application is wired to real data. Projects and repositories, the work-order queue with hold/release, the runs list with an event timeline, work-order detail, cost, and the activity feed are all backed by API read models rather than placeholders (epic #80; #163–#168). Pull-request merge state is now tracked, which two of the project's six headline metrics depended on (#216). The gaps a run leaves between stopping and being noticed are now recorded, feeding the detection-latency metric (#263). Operator-managed configuration — the Claude credential, dispatch and runner enablement, per-repository writes, budget ceilings — is moving out of hand-edited `.env` files and into the database, one table at a time: `operator_settings` now stores a plain value or a reversible AES-256-GCM ciphertext per key, never both or neither (a hand-written `CHECK` constraint enforces it, since Prisma cannot), and `operator_settings_revision` carries the single document-level version the eventual `PATCH` endpoint will require via `If-Match`. An absent row still means "read from `.env`" — nothing is seeded into either table (epic #332; #336). Operator-managed configuration now has a single declaration point: a registry naming every managed key with its environment variable, its zod schema, its default, whether it is a secret, and whether a change is `live`, applies only to work started from now, or needs a restart — with a synchronous, env-backed resolver behind it. Parsing lives in the registry so that an environment string and a database JSON value resolve to the same typed result, which they do not today: seven call sites compare `=== true` and one compares `!== 'false'`, so `true` and `'true'` currently disagree depending on which one reads them. No consumer reads it yet — this is the vocabulary the Control Center is built on (epic #332; #335). Secrets now have somewhere safe to go: an AES-256-GCM secret box seals operator-supplied credentials at rest with the setting key as additional authenticated data, so a ciphertext copied from one settings slot into another refuses to open rather than putting a credential to work where its owner never authorised it, and a decrypt failure is reported as an error instead of falling back to the environment value the operator had already rotated away from. It needs `OPIFEX_SETTINGS_ENCRYPTION_KEY` (32 bytes, base64) — absent, the API still boots and reads still fall back to `.env`, but storing a secret answers 503 naming the variable, and losing the key is unrecoverable. The same change redacts the system-settings audit rows, which today write the entire new settings document into `audit_events.meta`: harmless while that document holds a theme flag, and permanent the first time it holds a credential, since nothing added later removes a plaintext secret from an audit log's history (#337, epic #332). `/admin/settings` is now the Control Center rather than three tabs of application settings, and its landing view renders `docs/RUNBOOK-enable-claude-code-local.md` live: binaries installed, credential authenticates, runner enabled and dispatchable, dispatch on, at least one repository enabled — each step showing what an endpoint actually returned and naming the endpoint that returned it. Two of the five steps report **not yet verifiable** instead of a green check, and that is the feature: nothing publishes `DISPATCH_ENABLED`, and no probe authenticates the Claude credential, so the only signal that looks like one — a runner reporting `available: true` — comes from `claude --version`, which succeeds without credentials. Inferring a pass from it would automate exactly the failure epic #324 documented, where an unauthenticated CLI registers as healthy and every dispatched run then fails at auth after the work order was already authorized. Configured and observed are shown side by side and never merged, so `enabled: 0` sits next to `available: true` the way the runbook records it. The sections the rest of the epic fills in — operator settings, credentials, the repository ladder, change history — are reachable now and say which issue delivers them rather than claiming to be coming soon. The feature-flag record and the raw JSON editor were deleted rather than carried across: the flags had no non-test consumer, and an editor that bypasses per-field validation is a foot-gun once a credential or a spend ceiling lives behind it. `ui.allowUserThemeOverride` was kept and is still editable — it is the one system setting that changes behaviour today, and it already has a history of being a setting nothing honoured (#347, epic #332). Those stored values are now actually read: operator settings resolve `default -> env -> database row`, with an absent row falling through to the environment rather than reading as `false`, and the overlay reloading at boot, after every write, and every fifteen seconds. That timer is what recovers a boot that started without a database — the API retries three times and starts anyway (#161) — and until it does, the service reports `status: 'unavailable'` as a value the API returns and the cockpit can render, because a silent fallback to `.env` is indistinguishable from "no overrides exist", which is the whole failure this part of the epic is about. Writes go through `set`/`clear`, which put the row and the collection revision counter in one transaction so an `If-Match` cannot go stale against a half-applied change; a cleared key reverts to whatever the environment says, not to the code's default, since an env value is a choice the operator already made. Secrets are sealed into the ciphertext columns with the setting key as additional authenticated data, and a stored secret that will not decrypt marks that key `error` and resolves to "not configured" rather than falling back to the credential the operator rotated away from. Each write files an audit row of `{ key, from, to }` for the one key alone, masked — never the whole document (#339, epic #332). Two frozen reads in the GitHub layer are now resolved per use: `GitHubHttpService` captured the token, request timeout and retry budget into `readonly` fields at construction while `RunWorkspaceService` read the same token live, so a rotation already applied to git operations and not to a single HTTP call — a split brain that predated any UI. `GitHubWriteService` froze the write kill switch the same way, which meant flipping GitHub writes would have appeared to work and changed nothing; a kill switch you must restart to pull is not a kill switch. The API base URL and user agent stay frozen deliberately, because the ETag cache is keyed by request path rather than by host and swapping the host at runtime would replay one host's ETags against another (#341, epic #332). The reconciler and run-poller intervals now register unconditionally and check enablement inside the callback, which is what every `@Cron` task in the codebase already did. For the runner the old shape was not merely inert but dangerous: registration and dispatch admission both read the enable flag lazily, so a runtime enable would have registered a runner and started admitting work while no poller existed — runs would begin, never be polled, never conclude, and hold their dispatch slots. `RECONCILE_INTERVAL_MS` is the one key a callback check cannot honour, since `setInterval` fixes its period at the call that created it, so it re-registers on change behind a mutex and takes effect from the next tick (#343, epic #332). Enabling a repository is now something an operator does on a screen rather than with `curl`: the Control Center's Repositories section renders the four per-repository flags as the ladder the API always documented them as — observe, then mirror labels, then spec feedback, then dispatch — with each rung saying what turning it on permits and why it is separate from the one below. The ordering is the point rather than decoration: the observation week has to end one repository at a time and in stages, reading first, then writing a label, then writing prose to a human, then running, and four switches in a row would have lost the one thing their design was for. Afterwards the successes drop out of the selection and the refusals stay in it, so trying again re-sends only what has not already worked (#407, epic #403).

**Registering a repository now creates the factory labels on it.** `factory:ready` is the whole eligibility signal — the reconciler skips every issue without it — and GitHub's label picker only offers labels that already exist, so a repository registered without them could not be steered at all short of typing the label name by hand with no autocomplete. Registration now provisions the fifteen control-loop labels (`factory:*` input, `factory/*` mirror, `needs:*`/`tier:*` routing) with their declared colour and description; this repository's organisational labels (`bug`, `phase:*`, the component labels) are deliberately not among them, since nothing in the control loop reads them and creating them in somebody else's tracker is presumptuous. **Provisioning failing does not fail the registration**: ADR-0001's fine-grained personal access token grants access one repository and one permission at a time and emits no `x-oauth-scopes` header, so whether it can create a label is unknowable until it is tried — the repository is registered either way and the response's `labelProvisioning.status` says `refused` rather than `ok`, which is the "configured is not effective" trap epic #332 exists to stop repeating. `GET /api/repositories/{id}/labels` answers which labels exist as an observation with a `checkedAt`, per label rather than as a bare count, and `POST /api/repositories/{id}/labels` repairs the missing ones — idempotent, so a second run creates nothing and reports no error. When the labels could not be read at all — a refused, expired or absent credential, a 404, an exhausted budget — **every count on the report is null rather than zero**, because a token that cannot read a repository's labels establishes nothing about what is on it and `present: 0` would be a fact nobody found out; a repair refused at the write still carries real counts, since its read succeeded. It **never deletes**: a label on the repository and absent from the taxonomy is left alone, because deleting one strips it from every issue carrying it and the taxonomy knows names and colours, not which issues had them. It is also deliberately **not** gated by `github.writesEnabled` — that switch governs whether the factory acts on issues during a tick, and gating operator setup on it would mean the observation week could not be set up without turning on the writes the switch exists to withhold. The code taxonomy and `.github/labels.yml` are asserted to agree in both directions, so the API and `scripts/sync-labels.mjs` cannot provision different sets. **The Projects screen shows label presence as an observation, not as a setting.** Each repository's card carries an “N of M labels present” row beside the access test, with a `checkedAt` that visibly ages and a note that nothing re-checks it in the background — configured state and observed state are never merged. What is missing is named and grouped by kind rather than only counted, since an operator whose one absent label is `factory:ready` is in a different situation from one missing `tier:small`, and a **Create missing labels** button repairs a repository registered while the token could not write, without re-registering it. That button is withheld where pressing it cannot help — a `refused` or `no_credential` answer is not fixed by asking again — and says so where it would have been. A check that could not read the labels is never rendered as “0 of 15 present”: those answers carry no counts and no label list at all — the counts are null, and null means the read did not happen rather than that the repository has none — so “none are present” and “nobody could look” stay different facts with different fixes. A repair that GitHub refused after reading the labels keeps its count and names what is still absent, because that answer did find out; only a failure of the read itself blanks the numbers. Registering reports both outcomes at once when they differ — the repository is registered, and separately its labels are not there — because with a fine-grained token that combination is an expected result rather than an exception (#415, #195, #303).

**The queue screen steers several work orders at once.** Rows carry a selection and the toolbar applies **mark ready** or **hold** to it, which replaces the practical alternative — opening seventeen issues and editing a label on each, which nobody does. Nothing new is persisted and no second control surface is introduced: it is N sequential calls to the two steer endpoints that already existed, and the intent still lands as a GitHub label that the next reconciler tick acts on (VISION §3.3). There is no batch endpoint, deliberately — the only thing one could add over N requests is a transaction, and rolling six written labels back because the seventh was refused is precisely the wrong answer. **Partial application is treated as the ordinary outcome**: the result is reported per work order, the successes are never undone, the headline over a mixed run is always a fraction of what was attempted, and what did not land stays selected so a retry re-sends only that. **A suppressed write is never shown as a success.** With `github.writesEnabled` off the endpoints answer the same `202 Accepted` as ever, with `labelWritten: false` — the request is accepted and audited and no label reaches GitHub — so that is its own outcome with its own sentence, those work orders go into no pending state and stay selected, and the screen says the intent was recorded and nothing was written. Select-all is bounded to the rows on screen and can never reach the queue behind them. The two things a release does not do are stated beside the button rather than discovered afterwards: lifting a hold re-stamps `queuedAt`, so a released work order rejoins at the **back** of the queue rather than at the position it left, and no number of `factory:ready` labels clears a quarantine — that stays a human's act on GitHub, where the actor is verifiable (VISION §8, #49). (#421, epic #419)

**An epic now resolves to its child issues (#424).** Opifex did not model epics at all — no parent/child relationship in `schema.prisma`, no resolution anywhere in `apps/api/src`, and the epic template's _Child work_ checklist read by nothing — so "only work on this epic" had nothing to resolve against. `EpicChildrenService` answers it from GitHub's native sub-issues relationship where that is populated, and otherwise from the epic body's task list, recording on every result **which source answered** and why the native one did not. That fallback is not a hedge: the sub-issues endpoint was probed with this deployment's fine-grained PAT and _is_ available, but returns nothing for every epic in this repository, so an empty native result is read as silence rather than as an authoritative empty set. Resolution walks **one level by default** — "the issues directly listed here", not "everything under this" — because the first caller (#425) turns membership into label writes and a wider destructive action is not recoverable; transitive is opt-in and the depth walked is always reported back. Cycles terminate, a closed or unreadable child stays in the set with its state rather than vanishing from it, and **nothing is persisted**: membership lives in GitHub, so every result carries a `checkedAt` and is an observation rather than stored truth.

**An operator instruction now becomes a proposed diff of GitHub labels (#425, epic #419).** `POST /api/steering/proposals` takes a sentence — _"only work on issues 1, 2 and 3"_, _"work on epic #419 and hold everything else"_ — and returns the `factory:ready` / `factory:hold` operations that would express it, the blast radius as data (`unreadied: 17`, plus a written sentence), and every reference it could not resolve with a reason rather than an error. It writes nothing; `POST /api/steering/proposals/apply` carries the proposal back and writes. Three decisions are worth knowing before using it. **No model is invoked on the deterministic path** — an instruction naming explicit issue numbers is parsed in code, which is faster, free, reproducible, and cannot hallucinate an issue number (VISION §3.1/§7); the response says so, and the chat's settings are not read at all. **Apply re-checks every issue and reports drift**: an issue whose `factory:` labels changed since the proposal is skipped and reported, never applied, and one drifted issue skips its own operation rather than the batch. **Nothing about scope is stored** — the diff lands as labels and Opifex keeps no scope of its own, so the chat stays a translator rather than becoming a second dispatcher that the reconciler would have to arbitrate against. With `github.writesEnabled` off the operations are recorded and not performed, in `queue-steering`'s own vocabulary (`writesEnabled`, `labelWritten`, `reconciled: false`), and every apply files an `audit_events` row naming the operator, the instruction and what was done. Only `factory:ready` and `factory:hold` can be written: `factory:clear-quarantine` is rejected by validation, because #49 requires a human apply it on GitHub where the applier's identity is verifiable. An instruction the parser cannot read is reported, not failed — and no model is asked for it either, because the steering chat has no spend ceiling and a metered consumer with no cumulative bound does not run (`steering/chat-spend-gate.ts`).

**The steering endpoints get an operator to talk to: `/steering` (#426, epic #419).** Type an instruction, read the label diff it would produce, and confirm it as a second, deliberate act — the chat is a translator with a confirmation step in the middle, and it is **not a chat that does things but one that shows what it is about to do**. **Nothing is ever applied automatically**: not for a confident deterministic parse, not for a one-issue diff, not for an instruction with no removals in it, because an exception for the easy cases is how a confirmation step becomes decoration and the chat becomes a second controller (VISION §3.6). **The diff is the content and the prose is a caption on it.** The blast radius is stated above the operations from the API's own counts, in one sentence naming additions and removals together; the operations are split by `named`, so the three issues an operator typed are in a different section from the seventeen an "only" clause un-readies; and a removal is drawn by the same component as an addition at the same size in the same variant — removals first — so there is no prop that could make one the quieter half. Each operation shows the labels observed on its issue right now, which is the baseline drift is measured against, and that baseline is echoed back untouched on apply: narrowing it to the two steerable labels or dropping it would turn drift detection off while leaving the screen looking exactly as it does now. The proposal can be **narrowed** before it is applied by un-ticking issues; the headline above deliberately does not follow the ticks, since it states what the instruction MEANS and would otherwise read "nothing will change" over a proposal that removes two labels. Per-issue results are reported and failures stay on screen: a drifted issue names the label that moved and which way, a partial application is always a fraction of what was requested, and what landed is never undone to make the answer tidy. **`needs-interpretation` reads as the ordinary answer for prose, not as an error** — the model path is refused today for want of a chat spend ceiling — and it says which of the two applies (no model configured, or the spend gate refused) and what works instead: naming issue numbers explicitly, which is parsed in code and needs no model at all. A **409 reads as "this proposal is stale, ask again"** with the instruction kept and one button to re-send it, and the thirty-minute expiry is shown before it happens rather than discovered on confirming. With `github.writesEnabled` off, confirming says the operations were **recorded and not performed**, in the queue screen's own words for the same kill switch rather than a second sentence for it. The destination is gated on `workorders:write` — the string `SteeringController` enforces on propose as well as apply, and the one write permission any destination gates on, because unlike the queue there is nothing here for a reader to reach.

#### Phase 6 — Supervisor, observe-only

An advisory agent now runs on a schedule, off the request path, and writes proposals to a decision log — nothing more. `SupervisorModule` imports nothing that could dispatch, write to GitHub, or reach a runner, so execution is structurally impossible here, not merely unimplemented (#90, #221, #222). Three proposers feed it — decomposition, issue shaping, and spec-quality feedback — plus a failure-diagnosis proposer whose output is explicitly labelled a hypothesis rather than a finding (#223, #224, #225, #227). Postgres state renders into a bounded snapshot the supervisor reads (#220), it now has its own model adapter and its own spend ceiling, separate from execution's (#259, #286), and a daily brief ranks what needs a human's attention (#228). The model adapter is now bound unconditionally rather than only when `SUPERVISOR_MODEL_API_KEY` happened to be set at boot, and it resolves the key, the model name, the base URL, the timeout and the token ceiling on every call. Before this, an absent key at startup left the adapter out of the graph for the life of the process, so a key supplied afterwards reached a supervisor that had already concluded there was no model to call — the setting appeared to take and changed nothing until a restart, which is the failure the operator-settings work exists to eliminate. With no key configured what an operator sees is unchanged: the invocation refuses, the decision log still records the row with its model reported as `none`, and nothing crashes at boot. What changed is that the refusal now names the setting to fix instead of telling whoever reads it to bind a provider, and that supplying the key takes effect on the next hourly invocation (#344, epic #332).

The supervisor is no longer tied to one vendor. `supervisor.model.provider` — `SUPERVISOR_MODEL_PROVIDER` — selects `anthropic` or `openai`, and an OpenAI adapter now sits behind the same `SupervisorModel` port the Anthropic one has always used; nothing in that port changed to admit it, and no code outside `supervisor/invocation/` learns that a second vendor exists, which a governing test now asserts over the source rather than leaving as a claim in a comment. The default is `anthropic`, so a deployment that changes nothing behaves exactly as it did. The provider is resolved per call, not at boot, so switching it in the Control Center reaches the next hourly invocation rather than the next restart. **`SUPERVISOR_MODEL_BASE_URL` now defaults to empty and follows the provider**: an operator who switches vendor and forgets the URL used to post the new credential to the old host, and a base URL that names a provider's own published endpoint — the value `infra/compose/.env.example` used to ship — is treated as empty for the same reason, so existing deployments follow the switch too. A proxy or gateway URL is still an override and is still used exactly as given. The price table gains the Claude 4.5-and-later families, which previously priced at `null`, and the OpenAI models, so the supervisor's spend ceiling counts an OpenAI call rather than silently under-counting it; models whose published rate could not be established — notably the `daybreak-*-latest` aliases, whose pricing follows whatever they are repointed at — are deliberately left out, since an absent rate reports itself where a wrong one makes the ceiling confidently incorrect (#392, epic #391).

An operator can now see what their key can actually reach. `GET /api/operator-settings/supervisor-models` asks the configured provider for its catalogue with the configured key, gated as a settings read, so the supervisor's model can be chosen from a list rather than typed from memory — a typo in that free-text field previously surfaced as a failure once an hour in the decision log with nobody looking. The call bills no tokens on either provider, which makes it a credential check that costs nothing, and the response says so in a field rather than leaving a client to know it: the Test button beside it deliberately spends real money and is rate limited for it, and the two are not the same kind of action. Each model comes back marked against the floor the epic chose — 5.4 on OpenAI, 4.6 on Anthropic — and **a model id whose version cannot be read is returned marked, never dropped**. That fails open on purpose: model ids follow no stable scheme across vendors or across time, so the day one changes it is the newest and most desirable model that stops parsing, and it must not silently vanish from the dropdown leaving the operator no explanation and no way to select it. A failure is a 200 carrying a status rather than an error the UI has to interpret, and it distinguishes its causes: nothing configured yet, a rejected key, a host that never answered so the key was never judged, a credential that authenticated and was refused, and — the likeliest real mistake once there are two providers — a key shaped like the OTHER provider's, which "invalid key" would have described misleadingly and sent someone off to reissue a credential that was never the problem (#393, epic #391).

The provider, the key and the model are now one control on one screen. An operator used to save the supervisor API key on the Control Center's **Credentials** tab, press Test, and be told that `SUPERVISOR_MODEL_NAME` was not set — a setting that lived on the **Configuration** tab, as a free-text box with no list and no validation. That split is gone: the Credentials tab now carries a supervisor model panel holding the provider picker, the key card itself, and a **dropdown of the models that key can actually reach**, and the Configuration tab names those four keys and points at it rather than offering a second, worse editor for the same decision. Choosing a provider saves it and re-asks the catalogue, because a model list belongs to a provider and a stale one is worse than an empty one; replacing the key re-asks for the same reason.

Three things that panel does deliberately, each of which would be easy to get backwards. **A model whose version could not be read is offered and marked "version not recognised"**, worded as a gap in what this build could judge rather than as a defect — the likeliest reason an id fails to parse is that the model is newer than the naming rule, so calling it broken would push an operator away from the model they came for. **A configured model that the provider did not list stays selected**, with an explanation, since the model may be retired, or reachable only by another key or project, or simply unlisted — and silently clearing a working configuration because a filter no longer likes it would be worse than the free-text field this replaces. And **an empty list says which of six things happened**: nothing configured yet, a rejected key, a key shaped like the other provider's, a host that never answered so the key was never judged, a credential that authenticated and was refused, or anything else with the provider's own answer quoted. Listing models is presented as what it is — a free call that can be pressed as often as you like, reading `spendsTokens` off the response rather than hard-coding it — and it sits beside, not merged with, the Test button that makes one real billed call. `supervisor.model.baseUrl` renders its empty default as "follows the provider selected above", as a placeholder that is never written back, so an unrelated save cannot quietly pin it (#394, epic #391).

An Anthropic key and an OpenAI key can now be held at the same time. `supervisor.model.apiKey` was a **single** credential paired with a single `supervisor.model.provider`, so an operator with both could store only one: selecting the other provider produced an empty model dropdown — correctly, since the stored key was refused as `wrong_provider` — and the only way forward was to overwrite the key they had. It is replaced by one slot per provider, `models.<provider>.apiKey` and `models.<provider>.baseUrl` (`MODEL_ANTHROPIC_API_KEY`, `MODEL_OPENAI_API_KEY`, and the two base URLs), generated from the adapter list rather than written out — so a third adapter gets its credential slot, its environment variables and its Control Center card without an edit to the settings layer, and the settings layer still names no vendor. The base URL moved with the key because the key is _sent_ to whatever host is named: one shared override across two providers would post one vendor's credential to the other's gateway the moment a consumer switched. Switching a consumer's provider now selects the other stored credential rather than finding the same one, so it neither requires re-entering a key nor destroys one. **The Control Center holds both keys on one screen**: the supervisor model panel shows the selected provider's credential beside the model list it fills, and every other provider's card below it, marked as stored and not in use — showing only the selected one was the alternative and was rejected, because a screen that stops mentioning the other credential looks exactly like the failure where switching provider destroyed it. The billed **Test the key** button follows the provider and appears on the selected card alone: the probe makes one real call through the supervisor's own adapter, so a button on an idle credential would spend money answering a question about a key nothing is using. The endpoint field edits the selected provider's base URL only, and an unsaved one is discarded rather than carried across a provider change, since a proxy typed for one vendor is not an address for the other. Configuration gains a **Model credentials** section that names these keys and points at the Credentials tab rather than offering a second editor for the host a credential is sent to (#422, epic #419).

The supervisor and the chat now choose a provider and a model independently. `supervisor.model.provider` and `supervisor.model.name` described _the_ model because there had only ever been one consumer; epic #419 adds a second, and the two want different models for reasons that do not converge — instruction parsing is small, frequent and latency-sensitive, where a supervisory judgement is occasional and wants the stronger model. Four new keys, `chat.model.provider`, `chat.model.name`, `chat.model.timeoutMs` and `chat.model.defaultMaxTokens` (`CHAT_MODEL_PROVIDER`, `CHAT_MODEL_NAME`, `CHAT_MODEL_TIMEOUT_MS`, `CHAT_MODEL_DEFAULT_MAX_TOKENS`), arrive in a **Chat** section of the Control Center placed directly after Supervisor, because what an operator is doing there is reading one consumer's settings against the other's. The chat's provider and model are configured on the **Credentials** tab, in a panel of its own beside the supervisor's, with **the same filtered dropdown** #391 built rather than a free-text box — an operator picking one consumer's model from a list and typing the other's from memory was the asymmetry this issue removes. The timeout and the token ceiling stay ordinary controls in the Chat section: a timeout is not part of choosing a model. **The chat's panel carries no key field and no endpoint field**, and that is the credential split showing through: one key per vendor, shared by whoever selects it, edited once — so the chat names the slot it resolves to instead, and a provider the supervisor has not selected stops being described as idle when the chat is in fact asking with it. **Neither consumer carries a credential**: both resolve their key and their base URL from the per-provider slots #422 added, through one `resolveModelConfig(settings, consumer)` that is the only place either set of keys is read — so the supervisor can be on Anthropic and the chat on OpenAI at the same moment, each reaching the stored key for the vendor it named, and pointing both at one vendor shares that key rather than asking for it twice. The supervisor's own four keys, its environment variable names and its refusal messages are unchanged, byte for byte. **The timeout and the token ceiling are split rather than shared**, deliberately: the chat's timeout defaults to 30s against the supervisor's 60s because somebody is waiting on this one, and is capped at 55s because `proxy_read_timeout` is 60s in front of `/api` and a turn allowed past it is answered by the proxy with a 504 that says nothing about the model; its token ceiling defaults to 2048 against the supervisor's 1024, because a judgement is a paragraph and a proposed label diff is a list as long as the backlog it covers. `GET /api/operator-settings/supervisor-models` takes a `consumer` query parameter — defaulting to `supervisor`, which is what the route meant before — and echoes it back, so the two dropdowns filter by their own provider and a slow answer for one cannot land under the other (#423, epic #419).

**An unconfigured chat is inert and says why.** There is no `chat.enabled`: an empty `chat.model.name` _is_ the off switch, and it is the default, so an upgrade never starts a second metered consumer spending because a default said yes. A chat pointed at a provider with no stored key, or given a key and no model name, reports itself unavailable with the sentence naming which of the two is missing — the `available` versus `enabled` distinction #324 established — rather than failing at the first instruction. The Control Center says exactly that, in the same two words and in the same order (no key before no model, because a deployment with neither has configured nothing), and says it as **information rather than a warning**: a deployment that has not decided to run a chat has not made a mistake, and colouring the default state as a fault is how an operator learns to ignore the colour that means something. One predicate answers that question and it is the same one the adapters throw on, so a caller that asks before it calls and a call that refuses cannot disagree. Nothing calls it yet: the steering endpoint that will is #425.

**Upgrading.** A key stored from the Control Center is migrated at the next boot, into the slot of whichever provider the supervisor was set to — which is where it was already being sent. That migration is a decrypt-then-re-encrypt and could not be anything else: `common/crypto/secret-box.ts` binds every ciphertext to its setting key as AES-GCM additional authenticated data, deliberately, so that a stored blob cannot be copied between slots. A `key = ...` rename would have succeeded, left the Control Center reporting a credential as stored, and produced a row that nothing could ever open again. If the value cannot be read — a restored backup, a lost `OPIFEX_SETTINGS_ENCRYPTION_KEY` — nothing is moved, nothing is deleted, and the API says so at `error` on every boot until it is resolved, naming the slot and the remedy. Every stored credential is now read once at startup for the same reason: an unreadable one used to be discovered at the first model call, which for the supervisor is up to an hour later and in the middle of an unrelated failure. It is an error line and not a refusal to boot, on `secret-box.ts`'s own test — the API answers every other request correctly, and a process that stays up is the one that can be asked what went wrong.

**`.env` still works, for both keys.** `SUPERVISOR_MODEL_API_KEY` and `SUPERVISOR_MODEL_BASE_URL` are read as superseded names, so an upgrade does not take a supervisor offline at the restart that picks up the rename — the Credentials UI that would let an Admin rotate these from a form (#349) has not shipped, and these remain a plain `.env` edit until it does. Each superseded name feeds the **default provider's** slot only, and only while the new name is unset: one ambiguous variable cannot honestly name a credential for two vendors, and mapping it onto both would have put an `sk-ant-` key in the OpenAI slot — the confusion this removes, rebuilt by the shim meant to smooth it over. A deployment that set the old name _and_ selected a non-default provider is told so, by name, at boot. The new names are `MODEL_`-prefixed rather than the vendors' conventional `ANTHROPIC_API_KEY`, which is already taken by the `claude-code-local` CLI and is on the agent subprocess's inherited-environment allowlist — reusing it would have carried the separately metered supervisor credential ADR-0015 exists to keep apart into every agent that runs.

#### Phase 7 — Earned autonomy

The action-class taxonomy is now a single registry every proposer and grant reads from — the unit at which autonomy is ever granted is a class, never "the agent" as a whole (ADR-0011; #219). Trust grants layer on top of it: scoped, expiring, budget-capped authorizations to skip an approval for one class, gated by a per-class timeout, and renewable in one tap without ever widening scope (#96, #97, #115, #238, #243). A small, fixed set of effects is refused at the execution boundary regardless of any grant (#95, #235). Action classes promote on evidence and demote on regression, and a hand-demoted class is held off the ladder for a full regression window rather than re-promoting on the next good sample (#99, #240, #244, #281). A one-tap mobile approval surface and a cockpit view of trust grants and the promotion ladder ship for operating this by phone (#98, #101, #241, #245).

#### Phase 8 — Second runner

`claude-code-cloud` — the vendor-cloud runner VISION's roadmap named as the first candidate — was investigated and found blocked: the vendor CLI refuses non-interactive `--cloud` sessions, so required manifest fields are unobservable and its capability manifest cannot be honestly written. `claude-code-api` is documented as the resulting only viable second runner, but per VISION §3.7 is not built until its gate opens — this phase shipped a plan, not code (#112). Ahead of a second runner existing, dispatch gained the accounting a second one would need: a runner can report it exists but currently cannot take work, distinct from being unregistered (#105, #253, #266); dispatch routes around a runner whose subscription quota is observably spent, and ranks the two available quota signals by a stated precedence rule (#231, #248, #285, #300); and a "burn ratio" is deliberately **not** computed, since no vendor publishes the capacity it would need as a denominator — the metric stays `NOT_MEASURED` rather than a number nobody should trust (#231, #284). Quota windows are now recorded per runner and every live window is reported, not just the newest one (#301, #307). A cross-runner conformance suite exists so that a second runner, when built, has to prove it behaves like the first (#106, #250).

### Fixed

- The two `audit_events` sinks that echoed caller input now redact it by field name before the row is written. `UsersService.createAuditEvent` received `{ changes: dto }` — the raw `UpdateUserDto` straight off the wire — and `ObjectsService.createAuditEvent` received `{ metadataChanges: dto.metadata }`, which is arbitrary caller-supplied JSON: a client that puts an access token in a storage object's metadata wrote that token to `audit_events.meta` in plaintext, permanently. Both now pass their `meta` through `redactSettingsMeta`, at each service's single choke point rather than at the seven call sites, so a sink added later inherits the masking instead of having to remember it. **The masking is by field NAME, so the row still records that a field changed and what its non-secret siblings became** — `{ changes: { displayName: 'x', apiToken: '********6789' } }`, not a masked blob — which keeps the audit log answering the question it exists to answer. The four server-derived storage callers (`name`, `size`, `mimeType`, `partsCount`) are unaffected, since none of those field names is secret-shaped. The users sink carries no credential-bearing field _today_; the point is that an audit log is the one table nobody may go back and rewrite, so a redaction added after the first such field ships protects the next write and none of the ones already on disk (#361).

- An operator running Opifex behind a corporate egress proxy no longer gets an agent that can reach nothing, silently. `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` — and their lowercase spellings, which are the ones libcurl and several Node HTTP agents actually read — are now inherited by agent subprocesses. They were deliberately excluded when #334 replaced the inherited environment with an allowlist, and the exclusion had no escape hatch: the agent could not reach the Anthropic API or GitHub at all, while nothing named the cause, because `claude --version` needs no network and so the runner went on registering itself healthy while every dispatched run died at its first fetch. **A proxy URL that embeds credentials (`http://user:pass@proxy:3128`) is still refused**, since handing an autonomous agent a credential this process holds is the thing the allowlist exists to prevent — but the refusal is now loud and named rather than silent: the API logs it once at ERROR at boot, and the runner declares itself **unavailable** with the variable's name in its `unavailableReason`, so `/api/health/ready` and the Control Center's readiness chain say why before anything is dispatched. Neither case is inferred from the other spelling — what the operator set is what the child gets, because writing `HTTP_PROXY` from `http_proxy` would change what some clients do rather than being a safe no-op (#358, #334).

- A value the operator-settings registry refuses can no longer land on something MORE permissive than any value they could have written. Every rejected value used to fall back to the declared default, which is right for most keys and was a boundary-widening bug for two of the three #439 reported. `DISPATCH_MAX_CONCURRENT=200` — out of range, and a plausible thing to type when reaching for a high ceiling — resolved to `null`, meaning **no fleet ceiling at all**; it now falls back to the maximum, `128`, and "no ceiling" becomes something an operator states rather than something a typo lands on: the word `unlimited` (or `null`, or leaving the variable unset) is the only route to it. `GITHUB_API_BASE_URL=github.corp.example` — no scheme, so refused — resolved to public `https://api.github.com`, **sending a GitHub Enterprise deployment's fine-grained token to a host its operator never named**; there is no safer substitute to choose on somebody's behalf, so that one key now **refuses the boot**, names the variable, and says the default is a different host. It reads through the resolver rather than `process.env`, so a broken stored Control Center row is caught exactly as an environment variable is, and it names every offending key at once — `validateEnv`'s property, for `validateEnv`'s reason. Neither change touches what a CORRECT configuration does, and neither changes what an ABSENT one does: an unset variable still resolves to the declared default, because absence is a state the operator chose and a rejected value is not. `CLAUDE_CODE_PERMISSION_MODE=ask` — or `readonly`, or `plan-only`, all plausible spellings of _stricter_ — resolved to `acceptEdits`, a mode that lets the agent edit files; it now resolves to `plan`, the narrowest mode, which proposes and changes nothing. The six modes are ranked narrowest-first in `PERMISSION_MODES_BY_BREADTH`, beside the list of modes itself so the two cannot disagree, and a seventh mode added by the CLI fails the spec until somebody places it deliberately. Two of the three fallbacks cost something and it is deliberate: a rejected ceiling caps the fleet at 128 rather than leaving it uncapped, and a rejected permission mode produces runs that do no work. Doing less than was asked, loudly — both are `error` lines naming the variable and the value in force — is the intended direction; doing more than was asked, silently, is the bug. A **fourth** key #441's own table missed is covered too: `runners.claudeCodeLocal.gitRemoteBaseUrl` is `github.apiBaseUrl`'s hazard on the write path — its help has always said _"The GitHub token is sent to whatever host is named here"_ — so a rejected `GIT_REMOTE_BASE_URL` would have pushed an Enterprise deployment's token to public github.com, and it now refuses the boot alongside the other. The four default-**on** switches are deliberately NOT in this set: an unreadable value there is fixed at the parser instead (#439 reads `yes/no`, `1/0`, `on/off`), because a fallback to `false` would let one typo return a deployment to the inert posture ADR-0019 exists to end. `docs/operator-configuration.md` states all of it beside the resolution order (#441, #439).
- `tier:small`, `tier:standard` and `tier:large` now change which model runs. The labels were parsed, routed and recorded end to end, and then the `claude-code-local` runner never passed a `--model` flag — so `tier:small` and `tier:large` produced an identical invocation, and a work order recorded a tier it had not run under. The tier now resolves to a model through three operator settings (`CLAUDE_CODE_MODEL_SMALL`/`_STANDARD`/`_LARGE`, defaulting to `claude-haiku-4-5`, `claude-sonnet-5` and `claude-opus-5`), changeable from the Control Center because which model is "the cheap one" moves as models ship. A work order with **no** tier is still invoked with no `--model` flag at all and follows the CLI's own default — deliberately not the same as `tier:standard`, which pins one; naming today's default for the untiered case would have frozen it against a future CLI release. A tier this build cannot map runs on the default and is reported, never refused (#297's rule). Both facts are on the run record: `run.started` names the model that was asked for, and the CLI's own `init` line names the one it resolved (#420, epic #419).
- The database readiness check now performs a real round trip through `PrismaService.verifyConnection()` instead of reporting healthy on a client that was merely constructed (#161, #257).
- The API now boots without Google OAuth credentials configured, reporting the missing provider instead of failing to start (#138, #279).
- Seed drift — the database's permission rows falling behind the code that enforces them — is now detected and reported instead of manifesting as unexplained 403s while health checks still said `ok` (#173, #274).
- A run no longer writes to a column the `Run` model does not have (#159, #288, #289).
- The queue's cockpit labels no longer collide with the API's own status labels (#170, #270).
- The cockpit's theme override setting (`allowUserThemeOverride`) is now honoured; previously nothing read it (#211).
- The frontend now refetches when a filter changes instead of waiting for the next poll interval (#246, #256).
- Dispatch policy now carries a work order's model tier into its routing decision, with the projection under test (#265, #272).
- An ignored `needs:`/`tier:` routing label is now reported instead of silently swallowed (#297, #305).
- The seven routing labels are now declared in `.github/labels.yml`, so `scripts/sync-labels.mjs` creates them like any other. `needs:full-streaming`, `needs:cost-reporting`, `needs:structured-rate-limits`, `needs:own-infrastructure` (#64) and `tier:small`, `tier:standard`, `tier:large` (#273) existed only in code: an operator had to add all seven by hand, spelled exactly right, and a label that does not exist cannot be put on an issue — so a tier never reached a work order and `servesTier` never refused anything, which was #273's whole complaint arriving again by a different route. The taxonomy file's stated two-kind split is extended honestly rather than quietly: routing labels are named as a third kind, input like `factory:*` but describing what the work REQUIRES rather than whether it happens, and they take their own green colour band so a label that steers the factory and one that describes the work are not confusable on sight. `input-labels.spec.ts` now fails in both directions — a vocabulary entry in `ignored-labels.ts` that is undeclared, and a routing label declared in the file that the factory would ignore. `sync-labels.mjs`'s drift report now groups by kind and says what each kind costs, rather than printing a missing `tier:large` identically to a missing `factory:ready`: the first means work still runs and simply never leaves the defaults, the second means the repository cannot be steered at all. What the script DOES is unchanged — same labels created, same updates, same never-delete rule, same exit codes (#303).
- The reconcile log's `actionsExecuted` is now counted rather than hardcoded to `0`, which is what makes the observation week's daily check — _"it must be `0` on every tick, all week"_ — able to fail at all. It counts the GitHub writes a tick issued, measured at `GitHubWriteService`, the one place every write must pass through: mirror labels, spec-feedback comments, and the authorization record and branch a dispatch creates all land in it, including writes that changed nothing and writes that failed, since both reached GitHub. It stays `0` for as long as `GITHUB_WRITES_ENABLED` is off, so a non-zero value on a tick means something is enabled that should not be. Note that it is **not** a subset of `actionsComputed`: a spec-feedback comment and a dispatch branch are writes with no computed action behind them (#317).
- A reconciler tick now records which of its own acting-phase writes failed, and why, in `executionFailures` — so a tick that reports `actionsExecuted: 3` can no longer leave the one that threw recorded nowhere but a container log. Both executors report into one normalized shape, `{ source, actionType, repository, issueNumber, reason }`, and it is exposed on `GET /api/reconciler/ticks`. It is separate from `failures`, which stays observation-only, so no existing reader of that field changes meaning. `null` and `[]` are deliberately different: `null` means no acting-phase executor ran on that tick at all, `[]` means one ran and reported nothing wrong — writing `[]` for the first case would turn "never tried" into a clean bill of health. Note that a `reason` is not always a refused GitHub write: a label action carrying no label is reported here too, because the executor cannot tell the two apart and dropping it would hide a diff-engine bug. Dispatch's own write failures are still recorded on the run, not the tick (#320).

- Releasing a held work order now actually releases it. `POST /queue/{id}/release` added `factory:ready` and stopped, leaving `factory:hold` on the issue — and an issue carrying BOTH labels is held, because `issue-projection.ts` reads the hold from that label alone and `reconcileHold` reads the row from the same field. So the release wrote a label that changed nothing while every layer reported success: `202`, `labelWritten: true`, and, after #421, fifteen green results over fifteen work orders that stayed held. Release is now two writes, `factory:ready` added and `factory:hold` removed, in that order — add-then-remove fails CLOSED (the issue keeps both labels, the hold still outranks, the work order stays held), where remove-then-add would leave it with neither and re-queue a work order whose release the API had reported as failed. Hold is deliberately NOT symmetric: it adds `factory:hold` and leaves `factory:ready` alone, matching `SteeringService.namedOperation` (#425), because the two labels compose rather than contradict — ready means authorized, hold means paused — and removing the ready would make an issue with no work order yet project as `not-marked-ready` and vanish from the queue instead of appearing held. Because a release is two writes, half of it can land: that now answers **503** naming each write and what became of it, never a 202, since reporting a half-applied release as accepted would rebuild this same bug one level up. `labelWritten` accordingly now means every write in the plan reached GitHub, and the response carries a `writes` array describing each one. The kill switch still gates both writes, and the audit event is still written before the caller is told anything — including when the steer raises, which is the record an operator will be hunting for. Not observable on the reference deployment yet, since `github.writesEnabled` is off there and no issue has carried both labels (#432, #421, #425).

- The guided Claude sign-in now submits the code an operator actually pastes. `claude setup-token`'s input layer reads a single write above roughly 63 bytes as pasted TEXT rather than as keystrokes, and a paste carries no Enter — so the trailing carriage return in `write(code + "\r")` was absorbed into the pasted content and a real code sat at the prompt, echoed and unsubmitted, until the 90-second ceiling. Bisected against `claude` 2.1.246: 56, 60 and 62 characters submitted; 64, 65, 80 and 92 did not, and real authorization codes are around 92. The code now goes in wrapped in bracketed-paste markers, which is what a terminal sends for a paste and what the CLI asks for, and the Enter follows as a write of its own. The reason this passed every test for as long as it existed is that the fake CLI read the code with a shell `read`, which accepts a line of any length; it now models the threshold against a real pty, and reverting the production write to the single-chunk form fails the new 92-character test. Two failure reasons were split out of `timed_out` in the same change: `cli_no_url` (the CLI ran but never printed a sign-in link) and `cli_no_response` (it accepted the code and then answered nothing at all). Both used to render to the operator as "This sign-in expired", which was untrue, invited a retry of the thing that had just failed identically, and is what sent the diagnosis of this bug to read session lifetimes rather than the one write call at fault. `timed_out` now means only what its message always claimed: nobody pasted a code before the session's ten minutes ran out (#389).

- #422's boot migration now actually runs, and says so either way. On the reference deployment it moved nothing and logged nothing: the sealed `supervisor.model.apiKey` row stayed put, `models.anthropic.apiKey` was never created, and the credential an operator had entered became unreachable by any code path — with no line anywhere to distinguish that from a clean install with nothing to migrate. The cause was the hook, not the move: the migration ran in `onModuleInit`, beside the service that loads the settings overlay, and Nest starts every provider hook in a module together and awaits them with `Promise.all` — so the migration read `overlay().status` before its own first `await`, saw `unavailable`, and took a silent early return. Deterministic, not a race. It now runs in `onApplicationBootstrap`, after every module has initialised, and both "I could not check" arms — no database client, and an overlay that never loaded — log at `error` naming the superseded key and saying it is untouched and not in force. Only a deployment with genuinely nothing to migrate stays quiet, which is still every new one. **`UnreadableSecretsBootCheck` was silenced by the identical mistake** and moved with it, which means #422's other promise — a stored credential that will not decrypt is named at BOOT rather than at the first model call — starts holding on a running deployment rather than only in the specs that called it directly. Nothing about the move itself changed: still decrypt-and-re-seal under the new setting key, still write-the-new-row-then-delete-the-old in that order, still the same three named refusals, each of which leaves the superseded row exactly where it is. **An operator upgrading from a build with the stranded row needs no manual step**: the next boot performs the move that #422 promised, and reports it (#436, #422).
- The `Test API` CI job now provisions a real Postgres (matching `infra/compose/test.compose.yml`'s `opifex_test`) and applies migrations before the suite runs, so the database-backed `test/integration/*.integration.spec.ts` specs guarded by `describeIfDb` actually execute in CI instead of skipping unconditionally — one of them, `reconciler-actions-executed.integration.spec.ts` (#317), had gone red behind that skip for an unknown length of time, discovered only by reading the job log rather than by anything reporting it. The guard (now shared in `apps/api/test/helpers/database-guard.helper.ts`) still skips quietly on a developer machine with no local test database, unchanged, but fails loudly instead when the database is unreachable in CI — detected via the `CI=true` GitHub Actions sets on every job, not a bespoke opt-out that a future workflow could forget to set — turning a silent skip back into a red check (#440, #321).

- `npm run prisma:*` and `db:test`, run from a git worktree, now find `infra/compose/.env`. Both scripts resolved it with a fixed `../../../` offset from their own file, which is correct only from the main checkout — a worktree carries no `infra/compose/.env` at that offset, only the tracked `.env.example` — and `dotenv.config()` on a missing path is not an error, so every Prisma command run from a worktree (CLAUDE.md's mandated workflow for all development) silently fell back to the `postgres`/`postgres`/`localhost` defaults and failed later with a misleading connection error. Resolution now tries that same fixed offset first — so a deliberate, worktree-local `.env` still wins if one exists — then falls back to `git rev-parse --git-common-dir` to find the main checkout's copy from inside any worktree; if `git` is unavailable or the directory is not a git checkout at all (e.g. a container image with no `.git`), it falls back to today's fixed-offset-only behaviour rather than crashing. Every outcome is now logged — which file loaded and how, or a loud warning that none was found — instead of proceeding quietly (#322).
